# 初月500円お試しキャンペーン 対象者抽出 作業手順書（2026-07）

作成日: 2026-07-12
関連: `CAMPAIGN-500YEN-TRIAL-2026-07.md` §1（抽象的だった手順を、実際にクリックする操作レベルまで具体化したもの）
対象読者: 川崎さん、または運用担当（非エンジニア想定。専門用語には都度補足あり）
前提: このセッションからは実際のD1・Square・LINE管理画面のデータを見ることができないため、本書は「何を・どこで・どう確認するか」の手順書であり、実際の人数や一致件数を断定するものではない。

---

## §0 目的

「LINE友だち登録は済んでいるが、サブスク（月額契約）はまだしていない人」を洗い出し、500円お試しキャンペーンのメッセージを送る対象者リストを作る。
ゴールは、CAMPAIGN-500YEN-TRIAL-2026-07.md §3のメッセージテンプレを「誰に送るか」が一覧で確定した状態にすること。

---

## §1 現実的な抽出手順（ステップバイステップ）

### Step 1：LINE友だちの「総数」を確認する（分母の把握・5分）

1. https://manager.line.biz/ にログイン
2. 対象アカウント（FOLLOW公式）を選択 → 左メニュー「ホーム」を開く
3. 画面上部の「友だち数」（累計・ブロック除く）を確認し、メモする

**注意**：LINE公式アカウント管理画面には、個人を特定できる「友だち一覧（名前付きリスト）」をエクスポートする機能は基本的に無い（プライバシー保護のため、LINEはアカウント運営者に個々の友だちの本名・電話番号を渡さない設計）。ここで分かるのは**総数のみ**。個々の友だちが「誰か」を特定するには、次のStep 2でD1（顧客データベース）を見る必要がある。

### Step 2：D1の`friends`テーブルから個々の友だちリストを取得する（15〜20分）

`friends`テーブルは、LINE Bot（line-harness）が友だち追加のたびに1行記録している顧客識別用のテーブル（2026-07-11の調査で存在を確認済み。詳細は`LINE-BOT-FIX-2026-07-11.md`§3、`LAUNCH-GO-NOGO-CHECK-2026-07-11.md` B-5を参照）。

1. https://dash.cloudflare.com にログイン
2. 左メニュー「ストレージとデータベース」→「D1 SQL データベース」（英語表示なら Storage & Databases → D1）を開く
3. `line-harness`（または類似名）のデータベースをクリック
4. 「Console」タブを開く
5. 以下のSQLを実行する：
   ```sql
   SELECT * FROM friends ORDER BY created_at;
   ```
   （`created_at`のような日時カラムが無い場合はエラーになるので、その場合は先に `SELECT name FROM pragma_table_info('friends');` でカラム名を確認してから書き直す）
6. 結果画面に「Export」または「Download CSV」に相当するボタンがあればそれを使う。無ければ結果テーブルを選択してコピーし、Google Sheetsに貼り付ける
7. 取得した行数がStep 1の「友だち数」と大きくズレていないか確認する（大きくズレている場合、`friends`テーブルへの記録漏れがある可能性があるため、件数の一致率を必ずメモに残す）

**ここで得られる情報**：`line_user_id`（内部ID、人には読めない）、`display_name`（LINEの表示名＝ニックネームであることが多い）、登録日時など。本名・電話番号は基本的に入っていない（診断フォームで本人が入力していれば別。Step 4で扱う）。

### Step 3：現在の契約者（サブスク中）リストを確認する（15分）

以下の2つの情報源を、**上から優先順位順に**チェックする。

1. **既存のH-28campaign管理表**（`H-28campaign-SEND-2026-07.md`で管理している28名）
   - この28名は「**既存の契約者（サブスク中の顧客）**」であり、今回の500円キャンペーンの対象（未契約者）ではない。むしろ**除外リストとして使う**。
   - `F-sheets-setup-guide.md` Step 8に「G2（active_subscriptions）＝28」という記載があり、H-28の28名と一致している。つまり6月〜7月頭時点では、この28名が契約者のほぼ全数だった可能性が高い。
   - ただし7月に入ってからの新規契約・解約が反映されているかは不明。**そのまま鵜呑みにせず、次の2で最新状況を必ず確認する。**

2. **Square管理画面での最新の契約者一覧**（正の情報源として優先）
   - https://squareup.com/dashboard にログイン
   - 左メニュー「顧客」（Customers）、または「請求書・定期支払い」（Invoices → Subscriptions）を開く
   - 定期支払い（サブスクリプション）が「有効（Active）」状態の顧客一覧を表示
   - 画面右上あたりの「エクスポート」または「CSVエクスポート」でリストを書き出す（メニュー名は画面のバージョンにより多少異なる可能性があるため、「顧客」「取引」双方のタブでエクスポート機能を探す）
   - このリストの人数と、FOLLOW-KPI Sheetsの`daily`タブ直近行のG列（`active_subscriptions`）の数値、およびH-28の28名を突き合わせ、**現在の正しい契約者数**を確定する

**もし1と2で人数が食い違う場合**：2（Square側の最新データ）を正とする。H-28の28名リストは「6〜7月頭時点のスナップショット」として扱い、その後の増減分をSquare側で補正する。

### Step 4：診断フォーム回答データがあれば本名・電話番号を確認する（該当する場合のみ）

`B-line-bot-branch-logic.md`の設計では、カウンセリング（診断）完了時に顧客情報を入力するフローがある。もしD1に診断回答（`follow_diagnoses`テーブルなど）に本名・電話番号が保存されていれば、これがStep 2の`display_name`（ニックネーム）よりも突き合わせ精度の高い情報源になる。

1. Step 2と同じD1 Consoleで以下を実行：
   ```sql
   SELECT name FROM sqlite_master WHERE type='table' ORDER BY name;
   ```
2. `follow_diagnoses`や類似の名前のテーブルの中身を見て、氏名・電話番号らしきカラムがあるか確認する
3. あれば、`friends`テーブルの`line_user_id`と`follow_diagnoses`テーブルを紐づけて（同じ`line_user_id`で）氏名付きの友だちリストを作る

## §2 突き合わせ方法（LINE友だち × Square契約者）

### 前提の注意

LINEの`display_name`（ニックネーム）とSquareの契約者名（決済時の氏名）は、**別のシステムで別々に入力された名前**であり、同一人物でも表記が一致しない可能性が高い（例：LINEは「ゆき🌸」、Squareは「田中由紀」）。完全自動での突き合わせは期待しないこと。

### 手順（Google Sheets想定）

1. Sheetsに新しいシート「500円キャンペーン対象抽出」を作る
2. A列に、Step 2で得た`friends`リスト（`line_user_id`, `display_name`, 登録日）を貼り付け
3. 別シート「Square契約者」に、Step 3で得たSquareの契約者リスト（氏名, 電話番号, メールなど）を貼り付け
4. 突き合わせの優先順位：
   - **電話番号が両方にある場合**：電話番号でVLOOKUP／XLOOKUPを使う（最も信頼できる）
     ```
     =IFERROR(XLOOKUP(A2, Square契約者!C:C, Square契約者!A:A), "未契約 or 不一致")
     ```
   - **電話番号が無い場合**：氏名（表記ゆれ対策として前処理してから）で突き合わせる
     - 両リストの氏名列に対し、`=TRIM(SUBSTITUTE(A2," ",""))`のような式で全角/半角スペース除去・空白統一を行った補助列を作る
     - その補助列同士でVLOOKUP／XLOOKUPをかける
     - 完全一致しなかった行は、氏名を五十音順に並べ替えて**目視で似た名前がないか**確認する（例：「田中ゆき」と「田中由紀」など）
5. 一致した（＝契約者と分かった）友だちは「契約あり」、一致しなかった友だちは「契約なし＝キャンペーン対象候補」、判断がつかない行は「要確認」に分類する
6. 「要確認」行は、川崎さんに直接見てもらい、記憶ベースで契約有無を判定してもらう（人数が多くなければ現実的）

## §3 抽出結果を記録するシートのフォーマット案

シート名：`500円キャンペーン対象抽出`（FOLLOW-KPI Sheetsに新規タブとして追加、または別Sheetsでも可）

| 列 | 項目 | 内容 |
|---|---|---|
| A | line_user_id | D1 `friends`テーブルより |
| B | line_display_name | LINE表示名（ニックネームの可能性あり） |
| C | line_friend_added_at | 友だち追加日（D1にあれば） |
| D | 本名（診断回答があれば） | §1 Step 4で取得できた場合のみ |
| E | 電話番号（あれば） | 診断回答 or Square側から判明したもの |
| F | square_契約状況 | 契約中 / 契約なし / 不明 |
| G | square_登録名（一致した場合） | 突き合わせ元のSquare側氏名 |
| H | 突合方法 | 電話番号一致 / 氏名一致 / 目視推定 / 川崎さん記憶確認 / 判定不能 |
| I | 突合信頼度 | 高（電話番号一致） / 中（氏名完全一致） / 低（目視推定） |
| J | 500円キャンペーン対象 | Yes / No / 要確認 |
| K | 送信日 | メッセージ送信日（送信後に記入） |
| L | 返信有無 | あり / なし |
| M | 備考 | 自由記入 |

J列が「Yes」の行だけを抽出したものが、そのままCAMPAIGN-500YEN-TRIAL-2026-07.md §3のメッセージ送信リストになる。

## §4 想定される問題（正直な懸念点）

1. **LINE公式アカウント管理画面には個人特定できる友だちリストが無い**
   総数は分かるが、「誰が友だちか」はLINE管理画面単体では分からない。D1の`friends`テーブルに依存せざるを得ないが、このテーブルへの記録が全友だち分もれなく行われているかは未検証（Step 2の件数照合で確認する必要がある）。

2. **LINEの表示名は本名でないことが多い**
   ニックネーム・絵文字入り・イニシャルのみ等が多く、Square側の決済氏名と機械的に一致させるのは難しい。§2の突き合わせは「完全自動」ではなく「補助的な絞り込み＋目視ダブルチェック」が前提になる。

3. **友だち側に電話番号・メールが基本的に存在しない**
   LINEは友だち追加だけでは電話番号・メールを事業者に渡さない仕組み。診断フォームで本人が入力していた場合のみ§1 Step 4で回収できるが、全員がフォーム回答済みとは限らない（`B-line-bot-branch-logic.md` §7の通り、カウンセリング未完了のまま止まっている友だちも一定数いる設計）。

4. **`follow_diagnoses.status`は「支払い状況」ではなく「診断フローの進行状況」を表す可能性が高い**
   `LINE-BOT-FIX-2026-07-11.md` B-5の調査では、`status`の値として`waiting_counseling`や`waiting_current_photos`が確認されており、これは設計書（`B-line-bot-branch-logic.md` §3）にあった`new`/`counseling_done`/`paying`/`paused`/`cancelled`という**支払い状態を表すstatus定義とは別物**である可能性がある。つまりD1だけでは「契約中かどうか」を直接判定できず、**Square側のデータを正として使わざるを得ない**。この点は次回D1にアクセスできるタイミングで実際のカラム構成・値を確認して裏取りすること。

5. **H-28の28名がキャンペーン開始時点の契約者数と一致しているとは限らない**
   28という数字は6月時点のスナップショットであり、7月に入ってからの新規契約・解約が反映されていない可能性がある。§1 Step 3の通り、必ずSquare側の最新データで補正すること。

6. **代替案：名寄せが困難な場合**
   上記の理由で機械的な突き合わせの精度が低い場合、現実的な代替案は以下の通り：
   - 友だち追加時の表示名と、川崎さんが過去のLINEトーク履歴・カウンセリング内容から「この人は契約済みのはず」と記憶で判定できる範囲に絞り込む（H-28campaignの30秒判定フローと同じ発想）
   - 契約状況が「不明」の友だちには、いきなり500円オファーを送らず、まず「FOLLOWは今後も気軽にご相談くださいね」程度の軽いメッセージで反応を見てから判断する
   - **迷ったら送らない**（既存契約者に誤って500円オファーを送ると、割引の誤送信としてクレームや混乱のもとになるため、H-28キャンペーンの「迷ったらC（保守的判定）」の考え方をここでも踏襲する）

## §5 完了後にやること

1. §3のシートでJ列「500円キャンペーン対象」が「Yes」になっている行の一覧が完成する
2. この一覧が、CAMPAIGN-500YEN-TRIAL-2026-07.md §3のメッセージテンプレを**誰に送るか**の確定リストになる
3. CAMPAIGN-500YEN-TRIAL-2026-07.md §7の実行チェックリストのうち「§1 対象者リストを手動抽出」にチェックを入れる
4. 送信はH-28campaignと同じ運用（1日の送信数を制限、平日10:00–14:00、送信後は§3のK・L列に記録）で開始する
5. §4で「要確認」に分類された行は、川崎さんの最終判断待ちとして別途フォローする（無理に今回のキャンペーンに含めない）

## 補足：所要時間の目安

- §1 Step 1〜4（データ取得）：あわせて1時間前後
- §2 突き合わせ（Sheetsでの処理＋目視確認）：友だち数・契約者数の規模次第だが、数十名規模であれば1〜2時間程度
- 合計で半日以内に収まる見込み。ただし「要確認」行が多く出た場合は、川崎さんとの確認作業でさらに時間がかかる可能性がある。
